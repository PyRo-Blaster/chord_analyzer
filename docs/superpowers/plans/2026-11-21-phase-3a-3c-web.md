# Phase 3a–3c: API, Upload and Stem Mixer

Nov 21, 2026 · built on the Phase 1b pipeline (`jca_pipeline.orchestrator.analyze`).

**Goal:** the first three web slices of the design. A user uploads a recording, names the instruments (with presets), watches the job move through the five stages, and then plays the stems in a mixer with solo, mute, volume, download, a shared cursor, a loop and a 50–100% speed control.

**Architecture:** a FastAPI app in `api/` (package `jca_api`) depends on `core/` and `pipeline/` by path. It keeps a job table in SQLite and runs one background worker thread that calls `analyze()`; the heavy work already runs in the model worker processes. The React app in `web/` (Vite, TypeScript) talks to the API under `/api`. Playback uses the Web Audio API directly.

**Tech stack:** FastAPI 0.162, uvicorn 0.54, python-multipart 0.0.33, SQLite (standard library); React 19.3, Vite 8.3, TypeScript 7.0, Vitest 5.1, Testing Library, jsdom; Playwright 1.65 for the end-to-end test. Versions are the newest releases at least two weeks old.

## Decisions

| # | Topic | Decision |
| --- | --- | --- |
| 1 | Job queue | A SQLite job table and one worker thread in the API process, not Celery or Redis. The app is for one user on one computer (Phase 0), and the models already run in their own processes. |
| 2 | API shape | Every JSON response uses one envelope: `{"success", "data", "error"}`. Routes are under `/api`, so that the Vite dev server can proxy them. |
| 3 | Endpoints in this slice | `GET /api/instruments`, `POST /api/tracks`, `GET /api/tracks`, `GET /api/tracks/{id}`, `GET /api/tracks/{id}/stems/{name}`. `beats`, `chords`, the `PATCH` routes and export come with slices 3d–3h. |
| 4 | Upload limits | MP3, WAV, FLAC or M4A, at most 500 MB, streamed to disk in chunks. The instrument list is validated with `jca_core` before the job is queued. |
| 5 | Progress | The job row holds the status (queued, running, done, failed), the finished stages and the error. Progress is the share of the five stages finished. The UI polls every 2 s while a job runs. |
| 6 | Stems early | Stems are listed as soon as separation finishes, so the mixer opens before chord recognition ends. |
| 7 | Playback | All stems are decoded to `AudioBuffer`s and started on one `AudioContext` clock, so they stay sample-aligned. Each stem has a gain node; solo and mute are pure functions of the lane state. |
| 8 | Speed without pitch change | A WSOLA time-stretch in TypeScript, run in a Web Worker. The alignment offsets are computed once on the sum of the stems and applied to every stem, so the stretched stems stay aligned and still add up to the stretched mix. Results are cached for each speed. |
| 9 | Waveforms | Drawn on a canvas from peaks computed from each `AudioBuffer`, instead of wavesurfer.js. The playback engine owns the clock, so one cursor drawn over all lanes is simpler than keeping several wavesurfer players in step. |
| 10 | Track address | The page keeps the track id in the URL hash (`#/tracks/<id>`), so a reload or a shared link opens the same job. |

## Layout

```
api/src/jca_api/
  config.py        data folder, upload limit
  envelope.py      success and error envelopes
  jobs.py          Job model, JobRepository (SQLite)
  service.py       queue, worker loop, analysis calls (analyze is injected)
  schemas.py       request and response models
  app.py           FastAPI app and routes
  serve.py         jca-serve command (uvicorn)
api/tests/         repository, service and route tests with a fake analyze
web/src/
  api/             types and the fetch client
  upload/          UploadPanel, InstrumentForm, presets, JobProgress
  audio/           mix state, peaks, WSOLA, stretch worker, MixerEngine
  mixer/           Mixer, StemLane, Transport
  App.tsx, main.tsx, styles.css
web/tests/e2e/     Playwright: upload, progress, mixer, against a fake pipeline
```

## Tasks

Each task is test-first.

1. **API scaffold**: uv project, path dependencies, envelope helpers.
2. **Job repository**: create, get, list newest first, mark running, record a finished stage, mark done or failed; the data lives in one SQLite file and works across threads.
3. **Job service**: validate the request, save the upload in chunks with the size limit, queue it, run the next job with the injected `analyze`, record each stage, record failures.
4. **Routes**: instruments and presets; upload with form validation (400 with a clear message); status with progress, warnings, error and stem links; stem download with a correct content type; 404 for unknown tracks and stems.
5. **Web scaffold**: Vite, React, TypeScript, Vitest, a dev proxy to the API.
6. **API client**: typed calls that turn an error envelope into a thrown error with the server message.
7. **Instrument form**: the checklist, free text, presets (piano trio, quartet with one horn, quintet with two horns, big band), counts for horns; produces the request.
8. **Upload panel and job progress**: drop zone with format check, start button, polling, the five stages with their state, warnings and the error.
9. **Audio core**: mix state (solo and mute rules), waveform peaks, WSOLA with shared offsets (length scales with speed, pitch stays), engine with a fake `AudioContext` in tests.
10. **Mixer and transport**: one lane for each stem plus the residue, solo, mute, volume, download, shared cursor, click to seek, play and pause, loop a range, speed 50–100%.
11. **End to end**: Playwright runs the API with a fake pipeline (`JCA_FAKE_PIPELINE=1`) and the dev server, uploads a generated WAV, waits for the stems and checks the mixer controls.
12. **CI**: an `api` job and a `web` job (type check, unit tests, build).

## Exit gate

- [ ] The Playwright flow passes.
